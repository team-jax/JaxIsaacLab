### A-1. JAX 한 팔 로봇 이전의 준비: 휴머노이드 양팔 파지와 Franka Pick&Place 연습

> 주제: 1, 2 · 초안 출처: 시기 A (시작 ~ 10-19, Codex 시기)

- 날짜/기간: 2026-06 초 ~ 09-03 (문서 기준 v1 6월 초, v5 07-07, 문서 갱신 07-09, Franka 커밋 09-03)
- 상태 구분: 실행·검증됨(당시 시뮬 학습, 수치는 문서 기재값) / 이 시기 대화 원문은 확인 안 됨
- [상황]: 같은 "Team JAX" 이름으로, 실물은 "H1 기반 + 커스텀 손가락"이지만 시뮬에서는 Unitree G1 + Inspire 5손가락 손으로 대체해 양팔로 박스를 드는 과제를 했다(`TROUBLESHOOTING.md` 0절·8절). 손가락은 stiffness 2000으로 잠그고 팔 6 DOF만 학습했다.
- [목표]: 박스를 양손으로 잡아 들고 유지하는 보상 설계.
- [해결]: 보상 v1(접근·손바닥 방향·박스 자세 등 비접촉 보상) → "박스 근처 맴돌기"로 실패. v2 비접촉 보상 제거 → 한 손 전략·초기 만점. v3 양손 AND 조건 + 접촉이 있어야 들기 보상(contact-gated lift) → 윗면 누르기 꼼수. v4 측면 접촉만 인정 → 신호가 희소해 학습 불가(mean reward −0.81). v5 등급제(측면 접촉 1.0, 기타 접촉 0.2). 문서에 "태스크를 수행하지 않았을 때 보상 > 0 이면 잘못된 설계" 원칙과 체크리스트를 남겼다.
  9월 3일에는 Franka로 장애물이 있는 Pick&Place(`pick_place_obstacle`, 관측 66차원, 보상 reach 1·grasp_effort 12·lift 25·move_to_goal 10·place 50, 장애물 벌점 커리큘럼)를 만들고, `franka_pnp_env_cfg.py`의 `# [SWAP]` 5곳만 바꾸면 다른 URDF로 교체할 수 있게 구성했다(`RUNBOOK.md` "주요 설계 포인트").
- [결과]: v5 `2026-07-07_08-01-57` 2249 it, mean reward 145.59, 에피소드 길이 600/600(문서 기재). 학습률이 0으로 소멸하는 문제는 미해결로 남김. Franka 연습은 09-03 하루 4회 실행 폴더만 남아 있고 성공률 기록은 확인 안 됨.
  이 시기의 교훈(비접촉 보상의 꼼수, 윗면 누르기, 측면 접촉 판정의 희소성)은 이후 JAX 한 팔 파지에서도 **같은 형태로 다시 나타났다**(아래 [2·6] 사례들). 다만 이 문서를 JAX 한 팔 단계에서 참고했다는 직접 기록은 확인 안 됨.
- 근거: `git show 9780fdc8 --stat`, `9780fdc8:REWARD_DESIGN.md`(v1~v5, 버전별 비교표), `9780fdc8:TROUBLESHOOTING.md`(0절 현재 상태, 8절 "[중기] 실제 H1 + 커스텀 손 USD 통합"), `9780fdc8:RUNBOOK.md`; `logs/rsl_rl/h1_upper_body_reach/2026-06-11_*`, `franka_pick_place_obstacle/2026-09-03_*`; 메모 `project_custom_urdf_plan.md`(커스텀 팔+손 URDF를 G1 몸통에 붙일 계획, "Inspire 5손가락 손의 손가락 충돌 문제(손가락 바깥 꺾임)").

### A-2. 팀원 URDF 수령과 구조 결함 리포트: Humanoid_Assembly_Beta → One_Arm_JAX_URDF

> 주제: 1 · 초안 출처: 시기 A (시작 ~ 10-19, Codex 시기)

- 날짜/기간: 2026-09-08 ~ 09-24 (09-10 분석, 09-11 리포트, 09-24 재수출본 통합)
- 상태 구분: 결함 분석·리포트 = 실행·검증됨 / 메시 오프셋 굽기 수정 = 시도 후 되돌림 / 재수출본 통합 = 실행·검증됨(단독 스폰·짧은 학습)
- [상황]: 모델링 담당 팀원이 Fusion 360 계열 익스포터로 만든 `Humanoid_Assembly_Beta_description`(이름은 휴머노이드지만 다리 없는 고정 몸통 + 좌우 7자유도 팔 + 3손가락 그리퍼, 링크 29개)을 받았다(zip 09-08~09-10, 버전 4개). Isaac Lab에서 띄우자 사용자가 "관절이 다 잘리는 이유가 뭘까"라고 물었다.
- [목표]: Isaac Lab에서 학습 가능한 형태로 만들고, "잘려 보이는" 원인이 시뮬 설정인지 모델 자체인지 가리기.
- [해결]:
  1. (KST 09-10) 먼저 Isaac Lab 이식 시 걸릴 점을 정리: `package://`·`$(find ...)` 경로, Gazebo 태그 무시, `fix_base` 필요, fixed joint 병합, 고해상도 충돌 메시 비용.
  2. 메시 경로 58곳이 내보낸 사람 PC의 절대경로라 상대경로로 바꿨다.
  3. 물리 바디 위치와 렌더링 메시 bbox를 링크마다 비교. 처음에는 "임포터가 visual origin을 적용하지 않는다"고 보고 **오프셋을 STL에 굽는 우회 수정**을 했으나, 재검증에서 앞뒤가 맞지 않아 원본으로 되돌리고 USD xformOp를 직접 덤프했다(실패한 시도 포함).
  4. 최종 판단: 원본 URDF의 관절 원점 중 **R_shoulder_pitch→roll 0.662 m, R_wrist_pitch→yaw 0.730 m, R/L_wrist_yaw→rotation_base 0.380/0.450 m**가 이웃 관절 간격(6~19 cm)의 5~10배. 좌우 비대칭이라 미러링 실수가 아니라 관절마다 기준 축을 잘못 잡은 것으로 추정. 시뮬 설정으로 고칠 문제가 아니라 CAD에서 다시 내보내야 한다고 결론.
  5. 사용자가 "마크다운으로 정리해봐", "관절 정의 리포트 복사 가능한 형태로" 요청 → 리포트를 노션 페이지 "URDF 1차 보고"(09-11)로 만들어 모델링 담당에게 전달(요청 사항: ⚠️ 관절의 기준 축 확인, 상대경로로 재수출).
  6. (09-24) 재수출된 `One_Arm_JAX_URDF`(한 팔): 관절 오프셋이 모두 5~19 cm로 정상. 팔 8관절(어깨 pitch/roll/yaw, 팔꿈치, arm_yaw, 손목 pitch/yaw, 손바닥 회전 `rotation_base`) + 3손가락×2관절 = 구동 14개, `fix_base=True`. 링크별 물리–메시 위치 오차 2~7 cm로 끊김 없음을 스크린샷으로 확인. 팔이 −x로 뻗는 구조라 기존 Lift 테이블 배치에 맞춰 로봇을 180° 돌려 `Isaac-Lift-Cube-OneArmJaxUrdf-v0`로 등록.
- [결과]: 4 env, 150 it 짧은 학습과 60초 영상(`logs/rsl_rl/one_arm_jax_urdf_lift/2026-09-24_17-04-36/videos/train/rl-video-step-0.mp4`, 현재 삭제됨): 팔이 목표 쪽으로 뻗는 정도, 파지는 없음(mean reward 0.62). 씬 생성이 8분 넘게 멈춘 일을 처음엔 "노트북 절전 모드(powersave·PCIe Gen1)" 탓으로 추정했으나, 이후 정상 실행되자 "환경 수/카메라 설정 차이 때문이었던 것 같다"고 정정 — **원인은 확정되지 않음**.
  남은 한계: 이 시점 손가락 관절 이름과 child 링크 번호가 어긋나 있었다(Codex가 09-24에 지적, 손가락 1·2는 `wrist_yaw`, 손가락 3은 `rotation_base`에 연결).
- 근거: Claude 세션 `~/.claude/projects/-home-jeongwoo------Humanoid-Assembly-Beta-description/0bf87363...jsonl`(KST 09-10 17:50~); Codex 사본 세션 `~/.codex/sessions/2026/10/12/rollout-2026-10-12T17-33-10-01a12f3e...jsonl`(원본 Claude 세션 8617a74e); `~/다운로드/dbab8be2-..._URDF_1차_보고.pdf`(Created September 11, 2026); `~/다운로드/One_Arm_JAX_URDF_description.zip`(내부 시각 09-23 23:57, 수신 09-24); 자산 `source/isaaclab_assets/data/Robots/HumanoidAssemblyBeta/`, `OneArmJaxUrdf/`; 사용자 발화 "관절이 다 잘리는 이유가 뭘까", "One_Arm~~~ 된 파일 다운받아놨는데, 한 번 확인해주고 학습가능한형태로 만들어줘"(사본 세션, 원래 날짜 09-24 추정).

### A-3. 시뮬레이션 장면 구성: 의자 높이·정면 방향·책상 높이를 수치로 맞추기

> 주제: 1 · 초안 출처: 시기 A (시작 ~ 10-19, Codex 시기)

- 날짜/기간: 2026-09-24 ~ 09-25 (첫 배치), 2026-10-10 (새 환경 재검증), 2026-10-14~15 (V2 책상 거리)
- 상태 구분: 배치 변경 = 구현·짧은 실행 확인 / 정면 방향 = 수치 검증(두 번 정정) / 몸통 단축 요청 = 제안만 함(요청하지 않기로)
- [상황]: (KST 09-24 17:52) 사용자: "상체 중앙 몸통 길이가 팔 길이에 비해 너무 길어서 … 모델링 담당자에게 상체 중앙 길이를 줄여달라고 요청하는 게 맞는지도 판단해". 원래 장면은 로봇 root와 테이블 면이 모두 z≈0, 어깨 z=0.85 m라 실제 배치(의자 위 고정, 앞에 책상)와 맞지 않았다. 실제 치수는 미정(사용자 답 "미정 — 합리적인 시작값으로 설정").
- [목표]: 실제 사용 배치를 반영하고, 몸통 단축을 요청할 근거가 있는지 수치로 판단.
- [해결]:
  - (09-25) 좌면 0.43 m·상판 0.75 m로 시작 배치. 어깨–상판 높이차 0.85 → 0.53 m. 관절 한계를 적용한 기구학 탐색으로 물체 범위를 x 0.50~0.58 m, y ±0.06 m로 좁힘. **판단: 지금은 몸통 단축을 요청할 근거가 부족**, 실측 배치에서도 간섭이 반복되면 `base_link→shoulder` 0.85 m를 10~20 cm 낮추는 안을 CAD와 함께 검토.
  - 정면 방향: 처음엔 "이미 정면"이라 했으나 사용자 "안된거같은데 로봇 상체가 책상을향해야 한다니까"(KST 09-25 10:53) → 스크린샷으로 어깨바를 다시 보고 정면을 local −X에서 **+Y로 정정**, yaw 180°→−90°. 이 회전으로 물체 도달성이 부족해졌다고 함께 보고.
  - (KST 09-25 14:29) 사용자 지시로 **의자만 0.43→0.20 m로 낮춤**(URDF·yaw·책상 유지).
  - 7056 env에서 PhysX `totalAggregatePairsCapacity` 오류: Codex가 처음 기본값 4096을 실행값으로 잘못 읽고 1024 env를 권함 → 사용자 "근데 난 7056개 했을 때 저런 오류뜬건데" → 버퍼를 `32*1024`로 늘리는 쪽으로 정정.
  - (10-10, 새 direct 환경) 사용자: 영상에서 로봇 베이스의 "BACK" 표시가 작업대 쪽을 향한다고 지적. Codex 확인: 메시의 BACK은 base_link **+Y 면 → FRONT는 local −Y**, 기존 yaw 0°는 정면이 아니었다 → yaw −90°, `robot_front_world=(−1,0,0)`. 사용자 "바닥으로부터 120cm"를 base_link 메시 상단으로 해석해 root z 0.305 m, 어깨 z≈1.155 m. 책상 prim 원점 0.72 m가 아니라 **상판 0.74 m**를 기준으로 물체 중심 0.764 m. 4방향 렌더링 영상으로 FRONT가 작업대 쪽임을 확인(`artifacts/scene_validation_isaac.mp4`).
